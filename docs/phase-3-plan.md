# Phase 3: Agents

Phase 3 lets the model act, under the developer's permission, and lets the developer undo everything it did in one action. It adds the Agent Runtime (tool loop, permission tiers, taint tracking, task ledger), the Command Runner (a pseudo-console with a screen buffer, background processes, structured build and test logs), changeset preview and all-or-nothing apply in Visual Studio with checkpoints and a journal, the Agent and Terminal windows, the self-healing pipeline, the audit trail, workspace trust with repository rules and policy, and the evaluation and safety slices that judge all of it. It closes at Gate 3 and the private beta.

The design document is the specification: https://claude.ai/code/artifact/02f3ee51-8712-47d2-89af-3c7f6f1559fb (export in [design-document.md](design-document.md)). Section numbers below refer to it; sections 8 (Agent Runtime), 5 (changeset apply, tool windows), 12 (security) and 15 (evaluation) carry most of this phase. Phase 2's outcome is in [phase-2-plan.md](phase-2-plan.md) and [gate-2-report.md](gate-2-report.md).

## What phase 2 left us

- The Context Engine: an encrypted index per repository root, hybrid retrieval with `file:line` citations, the repo map, twelve `@`-mention kinds, workspace queries answered by Roslyn in devenv.exe (`FindReferencesAsync` and `CallersOfAsync`), the Index window, and conversations that survive a restart. Contract 1.3. Gate 2 ([gate-2-report.md](gate-2-report.md)): 14 of 19 rows pass; the three throughput and size rows pass against the CPU-tier targets the product owner restated on 2026-10-24 (issue #90); the keystroke p95 on Visual Studio 2026 is an open defect (issue #100); the offline run is the product owner's (issue #54).
- Stubs from phase 0 that this phase makes real: `IAgentService` (start, approve, deny, stop, revert), `IApprovalService` (host to VSIX, with tier, provenance and taint reason), `IEditorService` (`ApplyChangesetAsync`, `ShowPreviewAsync`, `GetOpenDocumentsAsync` with `Changeset` and `FileEdit`; the VSIX's implementation refuses every call), `PermissionTier` T0 to T3, the `Agent` task class, `RepositoryPolicy` (`.pillion/policy.json`, restrictive keys only, parsed but not applied to anything), the user-level `rules.md` path and the `ProjectRules` field of `ChatRequest` (nothing reads either rules file yet). On the workspace query service only `FindReferencesAsync` and `CallersOfAsync` are real; `GetSymbolAsync`, `GetDiagnosticsAsync`, `RenameSymbolAsync` and `RunTestsAsync` are forwarded to a not-implemented service in the VSIX. None of the agent stubs has an implementation in the host; the VSIX has no approval UI, no changeset view, no Agent or Terminal window.
- Pieces the runtime builds on: the redaction session with placeholder restore (`RedactionSession.Restore`, used by inline edit), Roslyn syntax validation in the host (`SyntaxValidator`, work item 1.8), IDE signals for builds, the debugger, the Error List, the Output panes and the running document table, LibGit2Sharp for `@git`, the Local Store with migrations, the eval harness (`tools/eval/Pillion.Eval`), the Gate 1 and Gate 2 suites and the integration-test projects for both Visual Studio versions.
- Decisions the product owner took on 2026-10-24 that are scheduled for this phase's first wave: lazy Error List and Output pane connection (issue #49), the ghost-text display rule with the dead early-display code removed (issue #51), the cancel rule for broker-started attempts (issue #52), the keystroke defect (issue #100), the secret scanner on chunk text at index time (issue #103), CPU-only ONNX Runtime as the default build (issue #78), and the truncated-embedding experiment judged by the retrieval harness (issue #90). Tech debt from Gate 2 that touches the same code: generated-marker false positives (issue #96), the old index serving during a model switch (issue #104), the untrimmed host at the 200 MB budget (issue #80).
- Not yet present anywhere: a pseudo-console, a VT parser, a binary-log or TRX reader, a Job Object for child processes, an audit trail, checkpoints, the apply journal, workspace trust, and any tool a model can call.

## Gate 3

The design names no one-line criterion for Gate 3 as it does for Gates 1 and 2; what it says is that phase 3 ends with the private beta, that the zero-escalation safety gate "is not negotiable" (section 17), and which evaluation sets are judged at Gate 3 (section 15). Gate 3 is therefore: **an agent completes multi-file tasks under approval with one revertible changeset, self-healing fixes seeded failures at the section 15 rates online and with the recommended local model offline, and the safety suite records zero auto-approved injected actions in every shipped approval mode.** Everything is measured on the reference machine (8-core CPU, 32 GB, 8 GB GPU), online and with the network disabled.

## Working agreement

- Gitflow as in phases 1 and 2: one `feature/<slug>` branch and one pull request per work item from `develop`, integrated through a wave branch when items depend on each other, merged with a merge commit once CI is green and the lead has reviewed it. Phase 3 adds the first `release/` branch for the beta build.
- Each pull request carries its unit and component tests and, for any in-process path, an integration test in both Visual Studio integration-test projects; nothing lands red. Tests that need a real model carry the `Live` or `Model` category and run in the gate, not in CI; the Command Runner's tests on a real pseudo-console run in CI.
- Every work item lands behind a feature flag: `features.agent`, `features.agentWindow`, `features.commandRunner`, `features.terminalWindow`, `features.changesetApply`, `features.selfHealing`, `features.projectRules`, and every tool behind its own switch under `agent.disabledTools`, which a repository policy can also set.
- Sub-agents do not change permissions, policy defaults or contracts without an entry in the decision log above or in the design document. In this phase that rule has teeth: a tool's tier, the sensitive-path list, the deny-list and the taint rule are specified in section 8 and may only be made stricter without a decision.
- Nothing an agent builds here runs a command, writes a file or reaches the network on its own during development either: the component tests use a scripted model and a scratch solution, and the gate scenarios run in the Experimental Instance against a copy of a generated solution.
- The product owner is asked only for decisions, the approval UX and safety reviews, and the gate review; the gate review for phase 3 adds the private beta build to the usual evidence.
